# 0.2.0 policy for `lair`, `treasure`, and `grappling`

Status: **decided** — applies to the Enraged Eggplant monster package from 0.2.0.

## The question

All 304 review candidates carry no populated values in three field families:

| Field family | Fields | Populated candidates |
| --- | --- | ---: |
| `lair` | `lair` | 0 / 304 |
| `treasure` | `money`, `items`, `strategy`, `change`, `estimatedMoneyAverage`, `estimatedItemAverage`, `estimatedMoneyPerAppearance` | 0 / 304 |
| `grappling` | `skill`, `damage`, `controlMaximum` | 0 / 304 |

Issue [#7](https://github.com/Zuljita/DungeonsOnAutomaticMonsters/issues/7) asks whether each family is required for
0.2.0, deferred enrichment, or intentionally unsupported.

## Does the authorized source provide values?

No. The authorized source is Enraged Eggplant's *Monsters* (May 11, 2024), a GURPS conversion of creature
**statistics**. Reading the full source corpus for the 304 converted creatures:

- **Lair.** The source has no lair, habitat, or terrain field of any kind. Some creatures mention an
  environment in flavor prose ("emerging from black saline cavern water"), but nothing structured, nothing
  consistent, and nothing that survives conversion as data.
- **Treasure.** The source has no treasure, wealth, or carried-items field. Treasure in the D&D-derived
  originals is edition-specific content that the fan conversion deliberately does not carry, and it is not
  ours to reconstruct from the SRDs under this package's licensing.
- **Grappling.** The source states no grappling skill, grappling damage, or control maximum. A handful of
  creatures state grapple-adjacent mechanics in prose (Constriction Attack, Binding, engulf), and those are
  now carried as explicit attack entries by the issue #5 repairs — but as attacks, which is what they are,
  not as the `grappling` control-maximum block.

## Decision

**All three families are deferred enrichment for 0.2.0, and ship as explicit nulls.**

1. `lair`, every `treasure.*` field, and every `grappling.*` field remain `null` in the released package.
   The objects themselves are always present with their full key sets, so consumers can read a field without
   an existence check.
2. Review does **not** synthesize values. A derived lair or a derived treasure yield would be DOA-authored
   content wearing the source's provenance, which is exactly what
   `provenance.conversionNotes` exists to prevent. Every record states this in its notes.
3. Grapple-shaped mechanics that the source *does* state are carried as attack entries with their real
   resolution (Quick Contest of ST, effective ST, pin/grapple thresholds), not squeezed into
   `grappling.controlMaximum`.
4. This is deferral, not abandonment. If a later package version obtains a source with real lair or treasure
   data, it populates these fields and states the derivation method in `conversionNotes` per the same rule
   the encounter metadata follows.

### Why deferral rather than "intentionally unsupported"

`lair` and `treasure` are live, meaningful fields for other Dungeons on Automatic monster sources — the
workbook-derived module populates them and the app's treasure generator consumes them. Marking them
unsupported at the schema level would break those consumers to describe a gap in *one* package. The gap
belongs to this source, not to the contract.

## Consumer behavior with nulls

The consumer contract already models all three families as nullable, so deferral needs no consumer change:

- `MonsterDef.lair` is `string | null`.
- Every `MonsterDef.treasure` field is `... | null`.
- Every `MonsterDef.grappling` field is `number | null` / `string | null`.

`scripts/test/field-policy.test.mjs` asserts the shape holds for every released record, and
`scripts/package-validation.mjs` requires the three objects to be present. The app-side null-rendering checks
are recorded in [`review/reports/app-site-export-review.md`](../reports/app-site-export-review.md).

## What the release notes must say

Public release notes for 0.2.0 disclose the deferral in these terms:

> This package ships monster statistics, attacks, ratings, encounter metadata, and art. Lair, treasure, and
> grappling values are not included: the authorized source states none, and the package does not invent them.
> These fields are present and null on every record. Grapple-style mechanics that the source does state
> (constriction, binding, engulf) are carried as attacks with their full resolution.

## Acceptance criteria coverage

| Criterion | Where |
| --- | --- |
| A package-wide policy exists for all three field families | this document |
| The schema and validators match that policy | `schema/monster.schema.json` (`lair` nullable; the three objects required), `scripts/package-validation.mjs` (`requiredObject` on all three), `scripts/review/field-policy.mjs` (null-shape enforcement) |
| Null behavior is covered by app and export tests when fields remain optional | `scripts/test/field-policy.test.mjs`; app-side notes in `review/reports/app-site-export-review.md` |
| Derived values identify their derivation method and do not masquerade as source mechanics | no derived values in these families; the encounter metadata that *is* derived states its rule in every record's `conversionNotes` |
| Public release notes disclose any deferred enrichment | the release-notes text above; mirrored in `docs/releases/0.2.0.md` |
